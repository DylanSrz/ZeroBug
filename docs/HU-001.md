**Para** desarrollar las funcionalidades de reservas, pedidos y operación del restaurante bajo un entorno estandarizado, modular, mantenible, escalable y fácilmente desplegable.

# Objetivo

Construir la estructura inicial del backend de la plataforma de gestión del restaurante siguiendo buenas prácticas de arquitectura, modularidad, desacoplamiento, validación, seguridad y persistencia de datos.

La solución deberá establecer una base técnica que permita desarrollar progresivamente las funcionalidades relacionadas con:

* Clientes.
* Empleados.
* Mesas.
* Reservas.
* Menú.
* Categorías.
* Productos.
* Pedidos.
* Cocina.
* Pagos.
* Inventario.
* Notificaciones.
* Reportes.
* Auditoría.

La aplicación deberá estar preparada para soportar diferentes ambientes de ejecución:

* Development.
* Testing.
* Production.

El entorno deberá poder levantarse de manera reproducible mediante Docker Compose.

```text

      ↓

      ↓

      ↓

      ↓

      ↓
```

La arquitectura inicial deberá permitir incorporar estos procesos progresivamente mediante módulos independientes.

# TypeORM

TypeORM será el ORM oficial utilizado para acceder a PostgreSQL desde NestJS (`@nestjs/typeorm`).

La arquitectura de persistencia seguirá conceptualmente el siguiente flujo:

```text
Controller
    ↓
Service
    ↓
Repository (TypeORM)
    ↓
PostgreSQL
```

El modelo de datos se define mediante **entidades** decoradas, una por tabla, ubicadas dentro del módulo de su dominio:

```text
src/modules/<dominio>/entities/<nombre>.entity.ts
```

Cada módulo registra sus entidades con `TypeOrmModule.forFeature([...])` y accede a ellas inyectando `Repository<Entidad>`.

La conexión de la aplicación se configura en `src/database/database.config.ts` con `autoLoadEntities: true` y **`synchronize: false`**: las entidades nunca modifican la base de datos por sí solas.

TypeORM será utilizado progresivamente para:

* Definir entidades.
* Definir relaciones.
* Definir enumeraciones.
* Ejecutar consultas.
* Crear registros.
* Actualizar registros.
* Eliminar registros.
* Ejecutar transacciones.
* Definir índices.
* Definir restricciones únicas.
* Administrar relaciones.

# Migraciones TypeORM

Todos los cambios estructurales realizados sobre la base de datos deberán administrarse mediante migraciones versionadas de TypeORM.

El sistema deberá conservar un historial versionado de las modificaciones realizadas al esquema en:

```text
src/database/migrations/<timestamp>-<Nombre>.ts
```

La CLI de TypeORM utiliza el `DataSource` definido en `src/database/data-source.ts`, que lee las mismas variables `DATABASE_*` que la aplicación.

El flujo esperado será:

```text
Modificar entidad
        ↓
Generar migración
        ↓
Revisar SQL generado
        ↓
Versionar migración
        ↓
Aplicar migración
        ↓
Actualizar PostgreSQL
```

Durante desarrollo se generan y aplican con:

```bash
npm run migration:generate -- src/database/migrations/NombreDescriptivo
npm run migration:run
npm run migration:show
npm run migration:revert
```

Al arrancar, la aplicación aplica automáticamente las migraciones pendientes (`migrationsRun: true`), tanto en local como dentro de Docker, por lo que `docker compose up` deja el entorno listo.

Las migraciones deberán importar los tipos de TypeORM con `import type { MigrationInterface, QueryRunner } from 'typeorm'` (Vitest no elide importaciones de tipos).

No deberán realizarse modificaciones manuales sobre la estructura de la base de datos que no estén representadas mediante una migración versionada.

# Variables de Entorno

Toda configuración dependiente del ambiente deberá administrarse mediante variables de entorno.

Entre ellas se contemplarán progresivamente:

```text
NODE_ENV
```

Las variables que todavía no sean utilizadas no deberán configurarse obligatoriamente durante esta Historia de Usuario.

```text
        ↓

        ↓

```

Los secretos y credenciales nunca deberán escribirse directamente dentro del código fuente.

# Validation

La aplicación deberá utilizar:

```text
class-validator
class-transformer
```

para validar y transformar los datos recibidos mediante solicitudes HTTP mediante DTOs con decoradores.

NestJS deberá tener configurado globalmente `ValidationPipe` con `whitelist`, `forbidNonWhitelisted` y `transform`: cualquier propiedad no declarada en el DTO produce `400`.

`zod` se utiliza únicamente para validar variables de entorno, no DTOs (decisión del equipo, issue #30).

Esto permitirá posteriormente validar DTOs correspondientes a:

```text
Reservas
Pedidos
Productos
Clientes
Usuarios
Pagos
Mesas
```

# Reglas de Negocio y Arquitectura

## RN-001

La aplicación deberá poder ejecutarse mediante Docker Compose.

## RN-002

Toda configuración dependiente del ambiente deberá obtenerse mediante variables de entorno.

## RN-003

La API deberá utilizar versionado y exponer sus recursos bajo el prefijo:

```http
/api/v1
```

## RN-004

Cada dominio funcional deberá encapsularse dentro de un módulo independiente de NestJS.

## RN-005

Los Controllers serán responsables de recibir solicitudes HTTP y delegar la lógica correspondiente.

No deberán contener directamente lógica compleja de negocio ni acceso directo a la base de datos.

## RN-006

La lógica de negocio deberá implementarse mediante Services o Providers especializados.

## RN-007

El acceso a PostgreSQL deberá realizarse mediante TypeORM.

No deberá accederse directamente a la base de datos desde los Controllers.

## RN-008

Todo cambio estructural realizado sobre PostgreSQL deberá estar representado mediante una migración versionada de TypeORM.

## RN-009

No deberán realizarse cambios manuales sobre el esquema de producción que no estén registrados mediante una migración de TypeORM.

## RN-010

Los datos provenientes del cliente deberán validarse antes de ejecutar la lógica de negocio correspondiente.

## RN-011

La aplicación deberá utilizar `ValidationPipe` globalmente.

## RN-012

La documentación Swagger deberá mantenerse sincronizada con los endpoints implementados.

## RN-013

Los secretos, contraseñas y credenciales no deberán almacenarse directamente dentro del código fuente.

## RN-014

La infraestructura deberá permitir incorporar futuras integraciones mediante API REST.

## RN-015

La arquitectura deberá permitir incorporar progresivamente eventos, WebSockets, colas, procesos programados y microservicios cuando las necesidades del sistema lo requieran.
